OBDonUDS P2Tester — Legacy vs Zonal AWS Benchmark

Built a measured automotive diagnostic architecture benchmark comparing a legacy central gateway with four distributed ECU diagnostic servers against a vehicle-centralized architecture using an ARM64 AWS Graviton HPC and four independent ZCU diagnostic servers.

01 / Engineering question

Does vehicle-centralized diagnostic routing consume more tester-visible timing margin?

The benchmark converts an architecture debate into a repeatable experiment: send the same diagnostic workload to four responders and compare tester-observed P2 timing when the responders are conventional distributed ECUs versus ZCUs behind a central HPC.

Verification question: under equivalent responder processing, network load, and request count, how do legacy distributed, zonal transparent-routing, and zonal application-proxy architectures compare at P50, P95, P99, maximum response time, and budget-miss rate?

ZCU boundary: each ZCU is the diagnostic server for the benchmark. There is no additional “Target ECU” behind the ZCU in this architecture abstraction.

04 / Transparent vs application proxy

Two different HPC behaviors

Transparent routing

The tester addresses the ZCU. The HPC forwards the DoIP diagnostic transaction while the ZCU remains the diagnostic service owner and response source.

Application proxy

The tester addresses an HPC proxy endpoint. The HPC terminates/parses the tester request, creates a new internal diagnostic request to the selected ZCU, waits for the ZCU result, and constructs the tester-facing response.

05 / Protocol realism

DoIP framing and raw UDS payloads instead of generic JSON timing messages

The measured harness uses the DoIP common header, TCP routing activation, and DoIP diagnostic-message payload type 0x8001 over TCP port 13400. The timing stimulus carries raw UDS ReadDataByIdentifier request/response bytes: 22 F1 90 and 62 F1 90.

This is intentionally described as a research harness rather than a complete ISO 13400 or SAE J1979-2 conformance implementation.

06 / Measurement method

P2Tester stays on one clock

Request transmission and response receipt are timestamped on the same external Tester EC2 monotonic clock. This avoids subtracting timestamps from different machines and makes the primary end-to-end timing statistic independent of clock synchronization.

  • Mean, P50, P95, P99, and maximum tester elapsed time.
  • Percentage of requests exceeding the selected engineering timing budget.
  • Per-ECU and per-ZCU P2Tester statistics.
  • Round-robin traffic across all four responders.
  • End-to-end traces retained for representative requests.

09 / Experimental controls

Stress the architecture, not just the happy path

  • Diagnostic responder profile: nominal, near-limit, or custom.
  • Configurable P2Tester engineering budget, including 50 ms studies.
  • Configurable request population distributed across four responders.
  • HPC application-proxy workload.
  • Legacy CAN-FD nominal arbitration bit rate, data-phase bit rate, and modeled bus utilization.
  • Automatic shutdown after the measured run.
