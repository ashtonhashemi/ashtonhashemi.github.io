OBDonUDS P2Tester — Distributed vs Zonal AWS Timing Lab

Built an automotive diagnostic-timing experiment to compare how a traditional distributed path, transparent zonal routing, and an HPC diagnostic proxy affect tester-to-response latency. The project combines an engineering timing model with a four-node AWS environment that measures real end-to-end TCP/IP timing across Tester, HPC, Zone Controller, and Target ECU processes.

01 / Engineering question

Does a zonal diagnostic path consume too much P2Tester margin?

The project was created around a practical architecture concern: a diagnostic request in a zonal vehicle may pass through central compute and a zone controller before reaching the target ECU, while a conventional distributed architecture may use a shorter tester-to-gateway-to-ECU path. The experiment turns that argument into a measurable verification problem rather than assuming that more logical hops automatically means more latency.

Verification question: for a selected P2Tester budget such as 50 ms, which architecture produces the lowest mean and tail latency, and under what target-ECU or HPC workload does the budget begin to fail?

02 / Architecture comparison

Three diagnostic routing strategies

Distributed path

Tester → Zone/Gateway → Target ECU

Represents the conventional shorter diagnostic-routing case used as the comparison baseline.

Zonal transparent

Tester → HPC → Zone → Target ECU

The HPC forwards the request without intentionally adding application-level diagnostic work.

Zonal HPC proxy

Tester → HPC proxy → Zone → Target ECU

The HPC terminates, processes, and reissues the diagnostic request, allowing proxy workload and scheduling cost to be studied directly.

03 / Measured AWS environment

Four independent EC2 roles

  • Tester EC2: originates diagnostic requests and measures the complete tester-to-response elapsed time using its monotonic clock.
  • HPC EC2: supports either transparent forwarding or an application-level diagnostic proxy with controlled local workload.
  • Zone Controller EC2: represents the zonal forwarding layer between central compute and the target ECU.
  • Target ECU EC2: returns a UDS-style diagnostic response after a controlled processing delay.

04 / Measurement method

Measure P2Tester on one clock; instrument every node locally

End-to-end P2Tester is measured entirely on the Tester EC2 monotonic clock, avoiding dependence on cross-machine clock synchronization for the primary result. The HPC, zone, and target processes also capture local processing times and observational timestamps so the measured total can be decomposed into target-ECU work, HPC work, zone work, and residual transport / operating-system overhead.

05 / Controlled experiment design

Paired ECU workload across architectures

The Target ECU simulator uses a deterministic seeded delay sequence so equivalent request numbers receive the same target-processing stimulus across the distributed, transparent-zonal, and HPC-proxy cases. This reduces random target variation and makes architecture-level differences easier to interpret.

06 / Model + measurement

Keep the model, verify it with real infrastructure

The dashboard deliberately provides two modes:

  • Timing model: Monte Carlo architecture trade study with explicit engineering assumptions for distributed, transparent-zonal, and proxy-zonal delay components.
  • Measured AWS: real multi-node TCP/IP execution using the four EC2 roles and actual end-to-end timing recorded by the Tester.

The model is useful for sensitivity analysis, including delay sources that AWS cannot physically reproduce as an in-vehicle bus. The measured mode is used to quantify the actual software, VPC, and routing overhead of the implemented architecture.

08 / Systems-engineering value

Architecture trade study tied to a measurable requirement

  • Requirement decomposition: separates tester-visible timing from target-ECU processing and architecture contribution.
  • Interface definition: defines explicit request/response contracts between Tester, HPC, Zone, and Target roles.
  • Architecture verification: compares distributed and zonal designs using identical workload and measurement criteria.
  • Tail-latency analysis: evaluates P95/P99 behavior and budget-miss rate rather than average latency alone.
  • Fault / timing thinking: exposes how queueing, application proxy work, transport delay, and near-limit ECU response time consume diagnostic margin.
  • Cloud-based SIL: uses reproducible infrastructure as code and automated orchestration to turn an architecture debate into a repeatable experiment.
09 / Implementation evidence

Deployed infrastructure; measured results generated at runtime

The public repository contains the timing model, Tester/HPC/Zone/Target processes, AWS SAM / CloudFormation infrastructure, Lambda control plane, SSM orchestration, dashboard, deployment scripts, and CI integration tests. The four-node AWS environment has been deployed successfully. Numerical measured P2Tester results are intentionally not hard-coded into this portfolio page; they are generated by actual runtime experiments and can be added after representative runs are completed.
